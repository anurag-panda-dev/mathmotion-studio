# Security MathMotion Studio

> **Status.** The MathMotion Studio application (FastAPI backend, React frontend, Manim renderer) **is not yet implemented** ([`ROADMAP.md`](ROADMAP.md)). This document therefore separates **Implemented** protections — verified in the reference validator [`tools/validate_scene.py`](../tools/validate_scene.py) — from **Planned** protections specified in `MASTER-PROMPT.md` §6–§9 and §12. Planned items are not claims about running software. Verification commands and real outputs: [`TESTING.md`](TESTING.md) §6.

Terminology: **scene.md** — the teacher-importable lesson file; **Scene format** — the restricted declarative format ([`prompts/SCENE_FORMAT_SPEC.md`](../prompts/SCENE_FORMAT_SPEC.md)); **Render job** — an animation-rendering task; **External AI** — the third-party assistant the teacher uses manually.

---

## 1. The core security principle

**MathMotion Studio never executes arbitrary Python returned by an AI.**

The product design rule (see `MASTER-PROMPT.md` §6, §8 and `SCENE_FORMAT_SPEC.md` §1) is:

- An External AI produces a `scene.md` file in the **restricted declarative Scene format** — YAML front matter plus fenced ` ```scene ` blocks.
- The application parses and validates that declarative format and translates validated actions into a **limited set of trusted Manim components** from a component registry maintained by the developers.
- No `eval`, no unrestricted `exec`, no dynamic import of user-supplied modules, no AI-generated Python script is ever run.

If a future contribution proposes "just run the Python the AI returned", it must be rejected. Declarative-format-only is a hard policy, not an implementation detail: it is the single control that makes importing untrusted AI output conceivable at all.

---

## 2. Trust boundary

**Everything inside a scene.md file is UNTRUSTED input.** It is machine-generated by an External AI, then handled by a nontechnical teacher, and may also arrive from a copied file of unknown provenance. Treat every byte of it — front matter, scene blocks, expressions, identifiers, strings — as attacker-controlled.

| Side | Trust level |
|---|---|
| Application code, trusted component registry, JSON schemas, validator logic | Trusted (developer-maintained) |
| scene.md content, file names, uploaded bytes, pasted Markdown | **Untrusted** |
| Render job output paths derived from untrusted content | Must be validated before use (Planned) |
| External AI responses | Untrusted by definition; may be wrong, malformed, or hostile |

Validation's job is to *reject* untrusted input, never to "interpret it safely". Per [`prompts/SCENE_VALIDATION_RULES.md`](../prompts/SCENE_VALIDATION_RULES.md) §4: reject, never guess; never silently discard unsupported constructs.

## 3. Implemented protections (Confirmed in `tools/validate_scene.py`)

Each row was verified by reading the code and, where noted, by executing the validator against hostile input ([`TESTING.md`](TESTING.md) §6).

| Protection | Implementation | Status |
|---|---|---|
| Safe YAML parsing | Front matter and every scene block are loaded with `yaml.safe_load` — never `yaml.load`/`unsafe_load`, so YAML tags cannot construct arbitrary Python objects. | Confirmed (code; both front matter and scene blocks) |
| No `eval`/`exec` for expressions | Math expressions are parsed with Python's `ast` module in `eval` mode and walked against an allowlist; the validator never calls `eval` or `exec` on scene content. | Confirmed (code) |
| Expression allowlist | Only numeric literals, `+ - * / **` (and `^` alias), parentheses, constants `pi`/`e`, variables, and 19 allowlisted math functions (`sin cos tan asin acos atan sqrt abs ln log log10 exp floor ceil round min max`). Keyword arguments rejected; attribute access, indexing, imports, lambdas, assignments, and calls to any other function produce error `unsafe_expression`. | Confirmed (code + hostile input rejected: `__import__('os').system('calc')` → `unsafe_expression`, exit 1) |
| Character-level pre-filter | The JSON schema additionally constrains `expression` strings to `[A-Za-z0-9_+\-*/^()., \t]`, rejecting obviously hostile characters before the AST check. | Confirmed (schema + hostile input rejected with `schema` error) |
| File size cap | Files over 512 KB are rejected (`file_too_large`) before any parsing. | Confirmed (code) |
| Encoding check | Content must decode as UTF-8 (BOM tolerated via `utf-8-sig`); otherwise error `encoding`. No encoding-confusion bypass into later stages. | Confirmed (code) |
| Schema-version gating | `schema_version` must equal a supported version (`1.0`); anything else stops the pipeline immediately (`schema_version`). | Confirmed (code + execution: `9.9` rejected, exit 1) |
| Strict JSON Schema validation | Both schemas use draft 2020-12 with `additionalProperties: false` — unknown fields are errors, so typos or smuggled instructions never silently pass. | Confirmed (schemas + code) |
| Resource caps | Per-file 512 KB; per-scene `maxItems`: 40 objects, 120 actions, 24 targets per id list; lesson metadata: 10 objectives, 10 prerequisites, 12 practice questions, 10 verification assertions; string length limits throughout. | Confirmed (schemas + code) |
| Reference & semantic checks | Unique scene/object ids; action targets must exist; `write` only on text-like objects; `transform.into` declared; graphs require `axes`; color must be a palette name or `#RRGGBB`; timing overflow vs. declared duration. Unsupported constructs are reported, never silently dropped. | Confirmed (code + execution) |
| Fail-closed behavior | Any error → exit code `1`; the pipeline stops at the first fatal stage; no partial result is produced. | Confirmed (code + execution) |

The validator itself performs **no network access, no subprocess spawning, and no writes** — it reads the file and prints a report. That was confirmed by code inspection (imports: `argparse ast json re sys pathlib dataclasses` plus `yaml`/`jsonschema` only).

## 4. Planned protections (Planned — application not yet implemented)

These are specified in `MASTER-PROMPT.md` §6–§9, §12 and [`prompts/SCENE_VALIDATION_RULES.md`](../prompts/SCENE_VALIDATION_RULES.md) §1; **none exist in running code yet**.

### Validation pipeline (14 stages, `MASTER-PROMPT.md` §7)

File upload/size → safe Markdown parsing → metadata parsing → schema-version validation → Pydantic schema validation → unsupported component/action checks → mathematical parameter validation → resource limits → optional mathematical verification (SymPy/NumPy, reported separately) → scene planning/layout → **trusted Manim scene generation** → **sandboxed rendering** → video/output verification → job completion/export. Structured errors carry category, scene id, field path, source line, explanation, and suggested correction; warnings never block, errors always do.

### Rendering isolation (`MASTER-PROMPT.md` §6, §8)

- Rendering runs in a **subprocess-based worker with bounded concurrency** and timeouts, never inside the API process and never on the FastAPI event loop.
- Generated Manim code comes only from the **trusted component registry** via typed constructors; untrusted text must never be interpolated into executable Python source without escaping and validation.
- Each Render job uses an **isolated per-job directory** for generated code, intermediates, and logs; temporary files are cleaned up after the job.
- Output integrity: a job is `completed` only after the video file exists, is non-empty, and is readable.
- Render cancellation, per-job logs, captured stdout/stderr, and honest (indeterminate where necessary) progress reporting.

### API hardening (`MASTER-PROMPT.md` §9)

- Versioned endpoints under `/api/v1` with typed request/response models and request validation.
- **Loopback-only binding by default** — the service must not listen on all network interfaces unless the user explicitly configures it.
- **CORS restrictions** scoped to the local frontend.
- **CSRF protection for state-changing operations** (import, render, delete, settings).
- Upload size limits; rate/resource limits appropriate for a local app.
- Consistent error responses, logging with request IDs; full stack traces stay out of the teacher-facing UI.
- **No general-purpose shell or Python execution endpoint** — permanently.

### File and path handling (`MASTER-PROMPT.md` §12)

- Safe filenames and unique job directories; **path-traversal protection**; no arbitrary overwrites; deletion confined to configured application directories (`data/`, `output/`).
- SQLite stores metadata only; large video files stay on the filesystem.

## 5. Local data storage and privacy

MathMotion Studio is local-first: SQLite metadata, scene.md copies, logs, and rendered videos stay on the teacher's machine (planned `data/` and `output/` directories; no cloud database, no accounts, no mandatory telemetry — planned). The one data flow the application does **not** control is the teacher's manual copy/paste to an External AI. Full treatment in [`PRIVACY.md`](PRIVACY.md).

## 6. Honest gaps and remaining limitations

1. **No sandbox exists yet.** Rendering is not implemented at all. Until the planned subprocess sandbox with timeouts and per-job directories lands, there is no runtime isolation to assess — and therefore no evidence that it works.
2. **The reference validator is not an application.** It has no authentication or access control because it is a local CLI; anyone who can run it can validate any file. That is acceptable for schema tooling and would not be sufficient as an import service.
3. **YAML safety is not resource safety.** `yaml.safe_load` prevents object construction, not resource exhaustion: a hostile deeply nested document could raise an unhandled resource error in the validator (bounded by the 512 KB cap). The planned upload pipeline adds explicit limits; see [`TESTING.md`](TESTING.md) §7.
4. **The External AI copy/paste step is outside our control.** The teacher — not the application — carries the prompt to a third party and brings the answer back. The application can validate the returned file rigorously, but it cannot verify that the teacher pasted only appropriate content, nor influence the External AI's own security or retention behavior. See [`PRIVACY.md`](PRIVACY.md) §2 and §4.
5. **Mathematical verification is separate from syntax validation.** A file that passes validation is well-formed, not guaranteed pedagogically or mathematically correct; `verification` assertions (Planned: SymPy/NumPy evaluation) address only the relationships they state. Never describe a scene as verified merely because it validates or renders.
6. **Known validator defects are documented, not fixed:** `--version` crashes with `NameError` (`SCENE_VERSION` undefined) and exits `1`; unquoted `schema_version: 1.0` is rejected with a confusing message. Full list in [`TESTING.md`](TESTING.md) §7.
7. **No security audit has been performed**, and no penetration test, fuzzing campaign, or dependency-vulnerability scan is automated today. None is claimed.

---

## 7. Reporting a security issue

If you find a vulnerability in the validator, schemas, or (once implemented) the backend, do not open a public issue with exploit details; contact the project maintainer privately and include: the file or endpoint affected, minimal reproduction input, observed vs. expected behavior, and affected version. Fixes to the Scene format's safety properties require updating spec, schemas, validator, and this document together ([`schema/README.md`](../schema/README.md)).
